# 08. The real database: what was wrong, how it was rebuilt, how it is tested

The test suite runs on a small, seeded **test** database (3 hotels; see `conftest.py`). This page is about the **real**
database the app uses when you run it from `.env` (`DATABASE_URL`, PostgreSQL on `localhost:5432`, database `hms`):
what we found in it, why it was rebuilt from scratch, what is in it now, and how to test the chatbot against it.

## 1. What we found in the old database

Everything in it was development or script-generated test data (confirmed by you), and it showed:

| area | problem | effect on the system |
|---|---|---|
| policies | 137 rows for 10 hotels in three naming styles: boilerplate copied to every hotel (`pet`, `check-in`, `check_in_check_out`, `cancellation`, `parking_valet`, `pool_and_spa`, ...) **plus** hotel-specific `*_policy` rows | contradictions shown to guests: Alpine Peak said both "pets under 40 lbs welcomed" and "strictly NO pets"; check-in 3 PM and 4 PM; Manhattan 72 h and 48 h cancellation; "infinity pools and cabanas" at a London townhouse |
| refund engine | reads `ILIKE '%cancellation%'` and takes the **first** row | with two cancellation rows per hotel, a guest could be quoted the wrong refund |
| knowledge base | only 74 of the 137 policies were synced; an *Amazon Leadership Principles* PDF uploaded as a hotel policy (11 chunks); PDF extraction had lost prices ("carve package: per day.") | stale, irrelevant and incomplete text in answers |
| users | 27 of 50 accounts auto-generated by test scripts (4 "Azure Staff" **admins**, "Jane Doe a92747", ...), test roles (`TestRole_23ef24`) | junk in the portal, needless admin accounts |
| hotels / rooms | 2 hotels without an owner, 4 without any amenities; room numbers repeated inside a hotel; "Suite 999"; Tokyo rooms on floor 1 of a hotel on floors 40-50 | broken portal views, implausible data |
| bookings | totals were placeholders (1,050 / 1,200 / 1,850 whatever the room or nights); stays from October still "in house" or "confirmed"; every `booking_rooms` row detached from its booking | wrong amounts, wrong status in the portal and in the chatbot's booking context |
| schema | 5 leftover columns the code no longer has (`bookings.assigned_room_id`, `assigned_room_ids`, `rooms_count`; `booking_rooms.booking_id`, `room_type_id`) | the cause of the detached rows above |
| search | the database has no pgvector extension, so search uses the Python fallback path, which no test had exercised | untested code path in production use |

## 2. The rebuild

Since none of the data mattered, patching it would have kept its shape problems. Instead
**`scripts/seed_demo_db.py`** rebuilds the database from scratch, and can do it again at any time:

1. drops every table and recreates them **from the current models** (the leftover columns are gone);
2. fills them from **`scripts/demo_content.py`**, where every fact about a hotel (check-in time, phone, cancellation
   tiers, fees, opening hours) is written **once**, and policies and documents are generated from those facts, so they
   cannot contradict each other;
3. builds bookings from **per-room calendars** (a room can never be double-booked), with statuses that follow from the
   date it runs: past stays completed, tonight's guests in house (and their rooms marked occupied), future stays
   confirmed, rooms allocated for arrivals in the next 14 days, about 7% cancelled; totals are always
   rate x nights x rooms; reviews only after completed stays;
4. loads the knowledge base through the app's own pipeline (`ingest_text`, then `sync_hotel_database_knowledge`);
5. **checks its own work** and stops with an error if anything is off: double bookings, wrong totals, statuses that
   contradict the dates, room status out of step with in-house guests, reviews on unfinished stays, duplicate policy
   types, customers without a guest record, hotels without an owner, and, most importantly, it runs the **app's own
   refund engine and check-in parser** on every hotel's policies and compares the result with the intended facts.

## 4. Code bugs found on the way

| bug | fix | proof |
|---|---|---|
| A hotel-scoped chat never told the model which hotel it was about; "Can we bring our 8-year-old?" was answered with "which hotel?" | the prompt now states the conversation's hotel and says unnamed questions refer to it (`chat_service`, "CONVERSATION SCOPE") | live Gemini, section 5 |
| The reviews chunk listed **every** review of a hotel in one chunk (now sent whole to the model) | the rating still uses all reviews; only the 8 most recent comments are listed (`document_service.sync_hotel_database_knowledge`) | offline tests |
| Re-ranking took ~2 s per question on the real data: one long chunk pads the whole batch to 512 tokens | the re-ranker reads at most `RERANK_MAX_CHARS` = 600 characters per chunk, pool `RERANK_CANDIDATES` = 20 | hit@1 0.87 → 0.90 **and** about twice as fast (section 5); `tests/test_rerank.py` |
| Refund engine takes the first cancellation policy it finds | data fixed (one policy per type, enforced by the seed's checks and the real-database audit); the code is unchanged | `scripts/seed_demo_db.py` self-check, `evals/real_db_check.py` audit |
| Receptionists could list every hotel's room assignments, booking guests and guest profiles; owners saw other owners' bookings and rooms | hotel scope on every operational route (`staff_hotel_scope`) | API check: receptionist sees 399 of 3,708 guests, another hotel's guest → 404, booking → 403 |
| Room check-in crashed (500) for managers and receptionists; check-in was allowed days before arrival | ownership check fixed; check-in only from the arrival date to the day before departure, with a room assigned | API check: early check-in → 400 with the reason, check-in on the arrival date → 200 |
| The concierge named the wrong "next trip" | next/current stay computed in code and given to the model | live Gemini via the API |

All of these are listed with details in `03-every-change.md`, D3.

## 5. Testing on the real database

**`evals/real_db_check.py`** tests the chatbot against this database **without changing it**:

* audit and search run in a `READ ONLY` transaction (PostgreSQL itself rejects any write);
* with `--llm`, every chat runs inside a transaction that is always rolled back, and the number of chat sessions is
  compared before and after (it stayed 0 → 0);
* Phoenix tracing is off for it, so test questions never mix with real conversations;
* it never imports `conftest.py`, which would point at, and wipe, the test database.

It has four parts:

1. **Data audit**: 14 checks that each return rows only when something is wrong (duplicate policy types, copied
   boilerplate, a check-in time outside the check-in policy, double bookings, wrong totals, stale statuses, reviews on
   unfinished stays, customers without guest records, chunks without embeddings, off-topic documents, missing prices...).
   Result on the rebuilt database: **no problems found**.
2. **Search quality**: 52 questions written from the real content (`evals/datasets/real_db_questions.jsonl`), each
   labelled with the text that answers it, scored vector-only vs re-ranked on the Python fallback path:

   | | hit@8 | hit@1 | MRR |
   |---|---|---|---|
   | vector only | 0.98 | 0.77 | 0.86 |
   | re-ranked | **1.00** | **0.90** | **0.95** |

   The one question vector search missed entirely ("Which of your hotels has a helipad?") is found first with
   re-ranking. The remaining "not first" cases are mostly the second chunk of the same cancellation document ranked
   above the first.
3. **Staff-only leaks**: public search for night-safe codes, dock gate codes etc. returned **0** staff-only chunks.
4. **Cross-hotel questions**: for "Which of your hotels allow pets?", the text of 6 hotels reached the model with
   vector search, 8 with re-ranking (of 10; 8 chunks are sent, see experiment #12 in `evals/baselines/EXPERIMENTS.md`).

**Live Gemini** (`--llm`): the 52 questions + a signed-in customer asking about their own booking ("If I cancel my
Alpine Peak booking today, how much would I get back?" → 100% refund of $1,840, 249.8 hours' notice, correct) and
asking for another guest's bookings (refused, none of that guest's booking ids or dates shown) + 3 cross-hotel
questions. Result: **55/55** exact checks (the first run, before the scope fix, was 52/55: two checker mistakes, now fixed, and the real "which hotel?" bug of section 4); chat sessions 0 before and 0 after.

The full 89-question golden regression on the test database, with re-ranking, whole chunks and the scope fix, then gave **86/89**: every category 100% except structured (14/17). The 3 misses are the same tool-routing kind recorded in experiment #7 (the answers were right, the expected lookup tool was not called).

## 6. How to

```powershell
# rebuild the real database (DROPS everything in DATABASE_URL; refuses a *_test database)
python -m scripts.seed_demo_db --yes

# test it (free; add --llm for live Gemini, ~60 requests, ~6 minutes)
python -m evals.real_db_check
python -m evals.real_db_check --llm

# restore the old database from the backup (pg_restore ships with PostgreSQL 16)
& "C:\Program Files\PostgreSQL\16\bin\pg_restore.exe" -h localhost -U postgres -d hms --clean --if-exists `
  "C:\Users\adity\Desktop\Internship\hms_db_backups\hms_before_cleanup_20261116_110236.dump"

# seed the Docker database instead (it has pgvector; the app container uses it)
$env:DATABASE_URL="postgresql://postgres:postgres@127.0.0.1:5433/hms"; python -m scripts.seed_demo_db --yes; Remove-Item Env:DATABASE_URL
```

**It stays current by itself (the autopilot).** A real hotel's data stays current because people operate it every
day. **`scripts/demo_autopilot.py`** does that work for the demo: each run it catches up on every day since the last
one: guests due to leave are checked out (after 11 AM) and their rooms freed; arriving guests get a room and are
checked in (after 4 PM; about 5% are no-shows, recorded as cancelled); rooms are allocated for arrivals in the next 14
days; new reservations come in for each elapsed day (about one per three rooms per day, 1-120 days ahead, capacity
checked per room type and night; requests for full room types are turned away); a few guests cancel future stays; some
departing guests leave a review and the hotel's knowledge base is re-synced. It keeps no state of its own: "days since
the newest booking was made" tells it how much to catch up, so running it twice on the same day adds nothing.

It runs inside the app when `DEMO_AUTOPILOT=true` (set in your `.env`): at startup and then every
`DEMO_AUTOPILOT_INTERVAL_HOURS` (3) in a background thread. It never runs on a `*_test` database, and the tests force it
off. To run it by hand: `python -m scripts.demo_autopilot`.

**Tested by time travel** on a scratch copy of the database: 120 simulated days, one at a time, plus one 10-day jump
(the app switched off for a week and a half). After every simulated day: no stale statuses, no double-booked rooms, room
status always matching the in-house guests, totals correct, reviews only on finished stays, and the business in a
steady state (48-53 guests in house, 51-58% of rooms occupied, 730-830 upcoming bookings).

You only need the seed again to start over, for example after changing `scripts/demo_content.py`.

## 7. Limits

* The content is fictional but internally consistent; photos are Unsplash images reused from the old data, and a few
  are shared between hotels.
* Reviews are composed from each hotel's real features, but not from the room the reviewer stayed in (a guest in a
  garden villa may praise the penthouse butler).
* The autopilot works on server time, not each hotel's local time zone (hotels store no time zone).
* The Docker app container (`hms-app`) uses its own database (`hms` on port 5433), which is still nearly empty, and runs
  code from before these changes; rebuild it and seed that database if you use Docker.
* The real-database question set is written by us from the content; it measures retrieval and simple facts, not every
  kind of conversation. The golden dataset (`evals/`) remains the main regression test.
